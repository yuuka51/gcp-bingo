# Google Cloud ビンゴ 仕様書(人間向け)

EARS形式の厳密な要件は `.kiro/specs/gcp-bingo/requirements.md` にあります。この文書は、全体像を短時間で把握するための読み物です。内容が食い違う場合は requirements.md が正です。

> **改訂メモ(2026-11-25)**: 進行メモを反映しました。主な変更は次のとおりです。
> - イベント時間を **30分** と想定し、時間管理機能(§8)を追加
> - **順位と景品の対応を最後に発表**する、ランキング・景品発表フェーズ(§9)を追加
> - 順位は **ビンゴの列数(ダブル以上)を優先**し、後半の盛り上がりを残す設計に変更
> - 同順位は **じゃんけん** で決める(アプリは同順位を表示し、並べ替えを助ける)
> - アプリが扱うのは **景品の数だけ**(景品名は扱わない)。ホストが開始前にカテゴリごとの数を設定する(合計20以上)
> - アプリは **ランキングを出すところまで**。景品の受け渡し管理は含めない
>
> `requirements.md`(`.kiro/specs/gcp-bingo/requirements.md`)は、この改訂に合わせて更新済みです。

## 1. これは何か

Google Cloud のサービス名をお題にした、イベント用のビンゴアプリです。

- ホスト(進行役)がお題を登録し、ルームを作る。
- 会場のスクリーンに QR コードを映す。
- 参加者はスマホで QR を読み取り、名前だけ入れて遊ぶ。
- ホストが抽選し、参加者は自分のカードの該当マスをタップして穴を開ける。
- 1列揃ったらビンゴ。全員に通知される。**ただし順位と景品は最後まで分からない。**
- 時間か景品数に達したら抽選を終え、ランキングと景品を発表する。

想定は約100人、**イベント全体で30分**です。アカウント登録はありません。

## 2. 技術の前提

| 項目 | 内容 |
|---|---|
| 使うもの | Firebase Hosting、Firestore、匿名認証 |
| 使わないもの | Cloud Functions、Cloud Run |
| 料金 | 無料の Spark プランに収める |
| 実装言語 | JavaScript(ES Modules)。TypeScriptやReactなどのフレームワークは使わない |
| フロント | HTML + CSS + JavaScriptをビルドなしで配信。SDK と QR ライブラリは CDN。Node はテスト実行だけに使う |
| 図 | インフラ構成図、DFD、フローチャートは `docs/diagrams.md` |
| 画面 | スマホ縦画面を第一に考える |

サーバー側のコードはありません。カード生成、ビンゴ判定、時間計算、ランキング集計はブラウザで行います。Firestore Rules は、誰がどのデータを読み書きできるかと、`ranking` 以降に書き込めないことを保証します。ランキング集計時には、ホストのブラウザが抽選済みのお題だけを使って全員のカードを再検証します。

## 3. 登場人物

| 役割 | どう決まるか | できること |
|---|---|---|
| ホスト | ルームを作った端末の匿名ID(UID)が `hostUid` になる | 時間管理、抽選、QR表示、参加者と達成者の確認、ランキング発表、ルーム終了 |
| 参加者 | 名前を入力して入室した人 | カードの確認、穴開け、ビンゴ、ランキングの閲覧 |

UID は匿名サインイン時に Firebase が自動で発行するランダムな文字列で、同じ端末・同じブラウザなら保持されます。サイトデータの消去、別端末、別ブラウザでは変わり、別人として扱われます。

## 4. 全体の流れ

ルームには3つの状態があります。

| 状態(`status`) | 内容 | 参加者の穴開け |
|---|---|---|
| `open` | 入室受付と抽選。時計を開始すると30分の進行が始まる | できる |
| `ranking` | 抽選を締め切り、ランキングと景品を発表している | できない |
| `closed` | イベント終了 | できない |

```
[ホスト]                               [参加者]
 お題JSONを登録
 ルーム作成(roomId発行)
 QRコードを会場スクリーンに表示 ───▶  QRを読み取る
                                      名前を入力して入室
                                      25マスのカードが自動作成
 「開始」で30分の時計をスタート
 「抽選」ボタン ─ お題を1つ確定 ───▶  抽選済み一覧に追加
 (サービス紹介の1分トークは司会)       該当マスをタップして穴を開ける
                                      1列揃う → ビンゴ演出 + 全員に通知
                                      (順位・景品はまだ出ない)
 時間 or 景品数に到達 → 終了を提案
 「抽選終了」(status = ranking)        穴開けが止まる
 「集計」で順位を算出
 同順位をじゃんけんで決め、並べ替え
 下位から順に発表 ───────────────▶  順位と景品が画面に出る
 ルームを終了(closed)
```

## 5. 画面

### 5.1 トップ(`/`)
ルーム作成の入口だけを置きます。ルーム一覧は出しません。

### 5.2 ホスト画面(`/#/host/:roomId`)

- **お題登録**: JSON の貼り付けまたはファイル読み込み。件数と一覧を表示し、不正な JSON は該当箇所を示します。24個未満ならルームを作れません。
- **景品数の設定**: 開始前に、ダブルビンゴ以上賞とビンゴ賞の数を入力します(合計20以上でないと開始できません)。
- **タイムキーパー**: 経過と残りの時間、フェーズごとの進み具合、予備時間を常に表示します(§8)。
- **QR表示**: 参加用URLのQR。いつでも出せて、全画面にでき、URLも文字で併記します。
- **抽選**: 「抽選」ボタンで未抽選から1つ選び、アイコン・名前・一言説明を大きく表示します。QR表示と切り替えられます。紹介トーク用の1分タイマーを添えます(任意で使用)。
- **抽選済み一覧**: 抽選順に表示します。
- **参加者一覧**: 人数、名前、識別コード。詳細でUID全文を確認できます。
- **達成者一覧**: 達成順に、名前、識別コード、列数、時刻を表示します。景品数に達したら「景品数に達しました。抽選を終えますか?」と提案します。
- **ランキング発表**: 集計、同順位の並べ替え、下位からの発表操作(§9)。
- **ルーム終了**: 確認のうえ `closed` にします。再開はできません。

ホスト以外が開いた場合は、操作を出さず参加用画面への案内を表示します。

### 5.3 参加者画面(`/#/play/:roomId`)

- **入室**: 名前を入力します(前後の空白を除いて1〜20文字、同名OK)。
- **カードタブ**: 5×5のカード。各マスはアイコンとサービス名だけで、中央は最初から開いたFREEです。操作はタップで穴を開けることだけです。
- **抽選済み一覧タブ**: 抽選された順に、アイコン・名前・一言説明を見られます。マスの説明を知りたい時はここを見ます。
- **ランキングタブ**: `ranking` 以降に表示されます。発表された順位だけが並びます。
- **ヘッダー**: 名前と識別コード(UIDの先頭6文字)を常に表示します。
- **状態表示**: 「抽選中」「結果発表中」など、いまのフェーズを短く出します。残り時間は参加者には出しません。
- **ビンゴ表示**: 揃った列数を「ビンゴ」「ダブルビンゴ」「トリプルビンゴ」…と表示します。ビンゴ時は「順位と景品は最後に発表!」と添えます。

## 6. ゲームのルール

### カード
- 入室時に、お題から24個をランダムに選んで25マス(中央FREE)を作ります。
- FREE は常に開いているものとして扱い、`marked[]` には保存しません。
- 保存されるので、リロードしても同じカードと穴の状態が出ます。作り直しはしません。

### 穴開け
- 抽選済みのお題のマスだけ開けられます。未抽選のマスは開けられず、短いメッセージが出ます。
- ビンゴ後も、`open` の間は開け続けられます(ダブル以上を狙えます)。
- `ranking` になると穴開けはできません。画面に「締め切りました」と出します。
- 1タップにつき、自分の `players` 文書への更新は1回です。

### ビンゴ判定
- 縦5、横5、斜め2の計12列のうち、1列でも5マスすべて開けばビンゴです(FREE込み)。
- 参加者画面の判定はブラウザで行い、サーバー側では検証しません。
- **順位を決める時は、ホストが改めて検証します**(§9)。

### 列数とダブルビンゴ
| 揃った列 | 表示 | 保存と通知 |
|---|---|---|
| 1列目 | ビンゴ(紙吹雪) | `bingoAt` を保存し、`events/{uid}` を作成。全員に「○○さんがビンゴ!」 |
| 2列目以降 | ダブル、トリプル… | `bingoCount` を更新するだけ。通知なし。ホストの一覧に列数が出る |

### 識別コード
同名の参加者を区別するため、UIDの先頭6文字を参加者画面とホスト画面の両方に表示します。景品の受け渡しでは、参加者が画面を見せ、ホストが一覧と照合します。端末を変えるとコードも変わります。

## 7. 抽選の仕組み

ホストが「抽選」を押すと、Firestore のトランザクションで次を一括して行います。

1. 現在の `drawn[]` を読む。
2. 未抽選のお題から1つランダムに選ぶ。
3. `drawn[]` の末尾に追加する。

複数のタブから同時に押しても順番に確定するので、重複や上書きは起きません。処理中はボタンを無効にして二重押しも防ぎます。`open` かつ時計の開始後だけ押せます。

## 8. 進行と時間管理

### 8.1 時間配分(既定値)

イベント全体を30分とし、**2分の予備時間**を持たせます。

| フェーズ | 既定 | 内容 |
|---|---|---|
| 導入・入室 | 3分 | QR表示、入室、ルール説明 |
| 抽選 | 20分 | 抽選、1分トーク、穴開け |
| ランキング・景品発表 | 5分 | 集計、じゃんけん、発表 |
| 予備 | 2分 | どこかが延びた時の余裕。フェーズには割り当てない |
| 合計 | 30分 | |

- 抽選フェーズの目安は **20回**(1回あたり約1分:抽選、1分トーク、穴開け)です。
- 既定値はホストが「開始」の前に変更できます。

### 8.2 タイムキーパー(ホスト画面)

| 表示 | 内容 |
|---|---|
| 経過 / 残り | イベント全体。「開始」ボタンで時計を始める |
| フェーズバー | 現在のフェーズと、その残り時間 |
| 予備時間 | 残りの予備時間。フェーズが延びると減る |
| 終了予定 | いまのペースで進んだ場合の終了時刻。30分を超える見込みなら赤で警告 |
| 抽選ペース | 「抽選 12回 / 目安 20回」のように実績と目安を並べる |
| 色の変化 | フェーズの残り5分で黄、2分で赤 |

- 時間が来ても **自動では遷移しません**。「抽選の時間です。ランキングへ進みますか?」と提案し、ホストが押して進めます。
- 開始時刻は `rooms` に保存するので、ホストがリロードしても時計は続きます。計算には端末の時計を使い、数秒のずれは許容します。
- 抽選の紹介トーク用に、1分のカウントダウンを置きます。トーク自体は司会が行います。

### 8.3 抽選の終了条件

次のどちらかに達したら、ホスト画面に終了を提案します。

1. ビンゴ達成者(1列以上)の人数が、**景品数の合計**に達した。
2. 抽選フェーズの時間が尽きた。

ホストは提案を待たず、いつでも「抽選終了」を押せます。

## 9. ランキングと景品

後半のしらけを防ぐため、次の仕組みにします。

- 最初に上がった人が自動的に上位になることを避ける。
- 順位と景品の対応は最後まで見せない。
- ダブル以上を目指す動機を残す。

### 9.1 景品数

- アプリが扱うのは **景品の数だけ** です。景品名は扱いません。景品表のファイルもありません。
- 賞は2つのカテゴリに分かれます。
  - **ダブルビンゴ以上賞**(2列以上)
  - **ビンゴ賞**(1列)
- ホストが、時計を開始する前に、カテゴリごとの数を入力します。既定値は5と15です。
- **合計が20未満だと開始できません。** 不足数が表示されます。時計の開始後は変更できません。
- 設定値は `rooms.prizes` に保存され、リロードしても残ります。
- 景品数の合計が、§8.3 の終了条件に使われます。
- 景品数は **ランキング発表の時まで参加者の画面に出しません**。ルール説明では、カテゴリがあることだけを伝えます。

### 9.2 順位の決め方

ホストが「集計」を押すと、全員の `players` から次の手順で順位を作ります。

1. **列を検証する**: 5マスすべてが「FREE」または「開けている かつ 抽選済み」の列だけを有効とします。抽選されていないマスを開けた分は数えません。
2. **列ごとの完成回を求める**: 列の完成回は、その列のマスのうち最後に抽選されたお題が **何回目の抽選か** です(FREEは0)。タップの速さには左右されません。
3. **有効な列数 `bingoCount`** を数える。0なら対象外です。
4. 並べ替えの順は次のとおりです。
   - `bingoCount` が多い順
   - 同数なら、`bingoCount` 本目の列の完成回が **早い順**
5. カテゴリで分け、各カテゴリの中で1位から順位を振ります。**1人は最も多い列数のカテゴリ1つだけ** に入ります。最初にビンゴした人が後でダブルを揃えたら、ダブルビンゴ以上賞だけに入り、ビンゴ賞の順位からは外れます。
6. **ダブルビンゴ以上賞の数を超えた人は、ビンゴ賞の順位に回ります。** ビンゴ賞の中の並びは、同じ基準(列数が多い順、同数なら完成回が早い順)です。

> 例: Aさんは5回目の抽選で1列、Bさんは15回目の抽選でダブル(2列)。Bさんはダブルビンゴ以上賞に入り、ビンゴ賞のAさんとは別のカテゴリで順位が決まります。

### 9.3 同順位とじゃんけん

- `bingoCount` と完成回が同じ人は **同順位** です(同じ抽選で同時に上がった人など)。
- 賞の対象範囲にかかる同順位の組だけ、ホスト画面に「じゃんけん」の印を表示します。賞外の組は解消しません。
- じゃんけんは会場で行います。結果をもとに、ホストが画面上で組の中の順番を上下ボタンで入れ替えます。
- 並べ替えた順はホスト端末の `localStorage` に保存し、Firestore には書きません。
- 賞の対象範囲にかかる同順位がすべて解消するまで、発表には進めません。

### 9.4 発表

1. ホストが「抽選終了」を押し、`status` が `ranking` になる(穴開けが止まる)。
2. 「集計」で順位を作る。
3. 同順位をじゃんけんで解消する。
4. 「次を発表」を押すたびに、**下位から1人ずつ** 発表する。カテゴリ順は「ビンゴ賞 → ダブルビンゴ以上賞」で、最後にダブル以上賞の1位が出ます。
5. 発表された人の `{ 順位, カテゴリ, 名前, 識別コード }` が、全員の画面に追加されます。
6. 発表が終わったら、ホストが `closed` にします。

- 両カテゴリの景品数を超えた順位(賞外)の人は発表に出ません。
- 1人は発表の中で1回だけ出ます。
- 発表していない順位は、`rooms` に書かれません。参加者の端末からも事前には見えません。
- 景品の受け渡しは、識別コードによる照合で行います。受け渡しの管理機能は作りません。

## 10. データ(Firestore)

| 場所 | 主な項目 |
|---|---|
| `rooms/{roomId}` | `hostUid`, `title`, `status`(open/ranking/closed), `topics[]`, `drawn[]`, `createdAt`, `schedule`, `rankingStartedAt`, `prizes`, `result` |
| `rooms/{roomId}/players/{uid}` | `name`, `card[]`(25要素), `marked[]`, `joinedAt`, `bingoAt`, `bingoCount` |
| `rooms/{roomId}/events/{uid}` | `type`("bingo"), `uid`, `playerName`, `at` |

追加した項目は次のとおりです。

- `schedule`: `{ startedAt, introMin, drawMin, rankingMin, bufferMin }`。`startedAt` が空なら時計は未開始です。
- `prizes`: `{ double, single }`。ダブルビンゴ以上賞とビンゴ賞の数です。既定は5と15で、合計20以上にします。
- `rankingStartedAt`: 「抽選終了」を押した時刻。
- `result`: `{ entries: [ { rank, category, uid6, name } ] }`。発表のたびにホストが末尾へ追加します。

お題は `{id, name, desc, iconKey}` で、ルーム文書の `topics[]` に入ります。`events` のIDをUIDにしているので、1人1件までしか作れません。景品名はどこにも持たず、景品の数だけを `rooms.prizes` に持ちます。

## 11. 誰が何を読み書きできるか(Rules)

| 対象 | 読む | 書く |
|---|---|---|
| `rooms` | 認証済みなら `get` のみ(一覧取得は禁止) | ホストのみ作成・更新。削除は不可 |
| `players/{uid}` | 本人とホストのみ | 本人のみ。ルームが `open` の間だけ |
| `events/{uid}` | 認証済みなら誰でも | 本人のUIDで、`open` の間に1回だけ作成。更新・削除は不可 |

- 未認証はすべて拒否します。
- `players` の更新は `marked`、`bingoCount`、`bingoAt` に限ります。名前とカードは入室後に書き換えられません。
- `marked[]` の中身は Rules では検証しません。技術に詳しい人は、抽選されていないマスを開けられます。ただし **順位の集計時にホストが検証する** ので、ランキングには影響しません(§9.2)。
- `ranking` 以降は `players` と `events` への書き込みを拒否します。

## 12. 読み取りの設計と無料枠

| 画面 | 購読するもの |
|---|---|
| 参加者 | ルーム文書、自分の `players` 文書、入室後の `events`(`at > joinedAt`)の3つだけ |
| ホスト | 上記に加え、全員の `players` |

全員分の `players` を購読するのはホストだけです。

追加分の目安(100人):

- 抽選1回ごとに、ルーム文書の更新が全員に届きます(約100件)。20回で約2,000件。
- 発表1人ごとにも同様です。発表人数を20人とすると約2,000件。

Spark の日次上限(読み取り5万件)に十分収まります。詳しい数値は design.md で示します。

## 13. セキュリティと公開

- ルームIDは Firestore の自動ID(20文字)で、推測できません。この秘匿性が唯一の入口の守りです。
- URLを知っている人は誰でも入室できます。会場のスクリーンにQRを映すと、URLは会場全員に見えます。READMEに明記します。
- 全ページに `noindex`、`robots.txt` で `Disallow: /` を指定します。
- 秘密情報は置きません。`firebase-config.js` と `.firebaserc` は `.gitignore` に入れ、`*.example` だけをコミットします。
- Googleのアイコン画像は含めません。`public/icons/` を `.gitignore` に入れ、`docs/icons.md` に取得手順と `iconKey` の対応を書きます。未配置の間は汎用プレースホルダーを表示します。
- フッターに「各サービス名・アイコンはGoogle LLCの商標です」と表示します。
- Rules は Firebase Emulator Suite でテストします。

## 14. 運用上の注意

- **ホストは同一端末・同一ブラウザで使います。** 端末を失うとホスト操作はできず、復旧もできません。その場合は新しいルームを作り直します。
- **参加者は同じブラウザで続けます。** QRリーダーアプリとブラウザが違うと、UIDが変わって別の参加者になることがあります。
- 本番前に、ホスト画面を開く端末を決めておきます。
- 「抽選終了」の前に、司会が「締め切ります」と声をかけます。押した瞬間から穴開けはできません。
- 1分トークは司会が行います。アプリは時間の目安を出すだけです。

## 15. 今回やらないこと

- ユーザー登録、ログイン画面
- チャット
- ランキングの永続的な保存(発表結果はそのルームの文書に残る範囲のみ)
- 景品の受け渡し管理
- 景品名の管理(アプリが扱うのは景品の数だけ)
- ビンゴの不正防止(サーバー側検証。ランキング集計時のホスト検証のみ行う)
- 複数ルームの管理画面
- ホスト端末を失った時の復旧
- 2列目以降のビンゴの全員通知
- 時間切れでの自動遷移
- GitHub Actions による自動デプロイ

## 17. 確認したいことの結果

要件定義書の未確認事項は、すべて決まりました。

| # | 論点 | 決定 |
|---|---|---|
| 18 | ダブル以上賞の数を超えた人 | ビンゴ賞の順位に回す |
| 19 | `open` から直接 `closed` | 許可する(中止用) |
| 20 | 順位の基準 | 列数優先。1人は最も多い列数のカテゴリ1つだけに入る |
| 21 | 景品の扱い | 数だけ。景品名は扱わない |
| 22 | 参加者への残り時間表示 | 見せない |

時間配分とお題数の相性は、`design.md` のシミュレーションで確認済みです。100人が抽選済みのマスをすぐ開ける前提では、お題40個のとき、20回の抽選でビンゴ達成者が平均約34人、ダブル以上が平均約6人でした。抽選20回、景品数20、ダブル以上賞5と釣り合うため、**本番用のお題は35〜40個を推奨**します。サンプルJSONは30件前後のままです。

インフラ構成、データの流れ、イベント進行、マスタップ時の処理、状態遷移は `docs/diagrams.md` にまとめています。
